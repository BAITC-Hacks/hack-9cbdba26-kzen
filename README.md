# KZen — рекомендации заказов поставщикам

Сервис для менеджеров отдела закупа ТОО «Электрокомплект». Он превращает выгрузки
из Excel в объяснимый список заказов по поставщикам: учитывает продажи, остатки,
товар в пути, сезонность, тренд, дефицит во время отсутствия товара и кратность
отгрузки. Менеджер проверяет и при необходимости исправляет результат, руководитель
утверждает версию, после чего сервис формирует файл для 1С.

Сервис **не отправляет заказ поставщику автоматически**. Последнее решение всегда
остаётся за человеком.

## Что реализовано

- загрузка и нормализация Excel-файлов IEK и Systeme Electric;
- связь файлов по коду 1С, а не по сокращённому наименованию;
- два детерминированных метода прогноза: `baseline` и `smoothed`;
- учёт свободного остатка, резерва, товара в пути, MOQ и категории;
- компенсация спроса за подтверждённые месяцы отсутствия товара;
- исключение разовых крупных продаж с сохранением подтверждающих данных;
- сезонность, ограниченный коэффициент роста и страховой запас;
- рекомендации, сгруппированные по поставщикам, со срочностью и обоснованием
  каждой строки;
- агент закупщика на правилах: проверка качества данных, расчёт и дополнительная
  проверка подозрительных позиций с журналом шагов;
- поиск, фильтры и сценарий «что если» в веб-интерфейсе;
- ручная корректировка количества с обязательной причиной;
- версии заказа, роли менеджера и руководителя, защита от утверждения устаревшей
  ревизии;
- экспорт утверждённой версии в XLSX или CSV для последующей загрузки в 1С;
- пять исполняемых проверок требований ТЗ и автоматические тесты;
- необязательное текстовое объяснение через OpenAI-совместимый API с безопасным
  откатом на локальный шаблон. Все числа в тексте берутся из расчётного ядра.

Это расчётное решение, а не обучаемая ML-модель: результат воспроизводим и может
быть разложен на составляющие формулы.

## Как работает решение

Основной пользовательский сценарий:

1. Сервис читает выгрузки продаж, остатков, товара в пути, MOQ и сезонности.
2. Данные двух поставщиков приводятся к общей структуре «артикул × месяц».
3. История очищается от разовых крупных продаж, затем компенсируются месяцы
   подтверждённого stockout.
4. Прогноз учитывает регулярный спрос, тренд и сезонность месяца поставки.
5. Из потребности вычитаются свободный остаток и релевантный товар в пути,
   результат округляется вверх до MOQ.
6. Агент отмечает позиции с недостатком данных или повышенным риском и сохраняет
   результат как новую версию.
7. Менеджер изучает формулу по шагам, корректирует позиции с указанием причины и
   отправляет версию на согласование.
8. Руководитель утверждает актуальную ревизию. Только после этого доступен экспорт
   XLSX/CSV; отправки поставщику в системе нет.

Упрощённая формула потребности:

```text
очищенный спрос
  → компенсация stockout
  → прогноз × рост × сезонность
  → потребность на срок поставки + страховой запас
  → минус свободный остаток и товар в пути
  → округление вверх до MOQ
  → срочность и объяснение
```

Подробные формулы, границы коэффициентов и допущения приведены в
[`docs/methodology.md`](docs/methodology.md). Описание исходного кейса и ловушек
в данных — в [`CASE.md`](CASE.md).

### Исключение разовых крупных продаж

Очистка выполняется до компенсации stockout и прогноза:

1. Транзакции используются как подтверждение, но не заменяют полную помесячную
   историю. Накладная становится кандидатом, если её объём не менее чем в 10 раз
   выше медианной накладной по SKU и составляет не менее 50% доступной
   транзакционной истории.
2. Для помесячного выброса ожидаемым уровнем служит медиана того же календарного
   месяца в другие годы; при нехватке наблюдений — медиана положительной истории.
3. Значение выше трёх ожидаемых уровней заменяется ожидаемым, а не удаляется:
   обычный спрос месяца сохраняется.
4. Повторяющийся сезонный пик не считается разовым заказом. Номер накладной,
   месяц и исключённый объём остаются в обосновании.

В выгрузках нет ID клиента, поэтому проверяемым приближением для «крупной продажи
одному клиенту» служит номер накладной.

## Технологии

| Часть | Технологии |
|---|---|
| Backend | Python 3.11, FastAPI, Pydantic, Uvicorn |
| Расчёты и Excel | pandas, NumPy, openpyxl |
| Frontend | React 19, TypeScript, Vite |
| Кэш | память процесса; Redis — необязательный адаптер |
| Текстовые объяснения | локальный шаблон или OpenAI-совместимый Chat Completions API |
| Тесты и качество | pytest, Ruff, oxlint, TypeScript compiler |
| Запуск | Make, Docker Compose |

Внешние сервисы для расчёта и прохождения тестов не нужны. LLM только формулирует
готовое обоснование и не влияет на рекомендуемое количество.

## Архитектура

```text
React UI
   │ HTTP /api/v1
   ▼
api/              маршруты, схемы и обработка HTTP-ошибок
   │
   ▼
application/      сценарии расчёта, агента, версий и интерфейса
   │
   ▼
domain/           сущности, формулы, статусы и порты без FastAPI/pandas
   ▲
   │
infrastructure/   Excel, прогнозы, кэш, LLM и экспорт XLSX/CSV
```

Зависимости направлены внутрь: `api → application → domain`, а инфраструктурные
адаптеры реализуют порты домена. Конкретные реализации собираются один раз в
`backend/app/core/container.py`. Тяжёлые расчётные эндпоинты объявлены обычными
`def`, чтобы FastAPI выполнял их вне event loop.

Основные каталоги:

```text
backend/app/domain/           расчётные правила и workflow
backend/app/application/      use cases
backend/app/infrastructure/   Excel, прогнозы, кэш, LLM, экспорт
backend/app/api/              REST API
frontend/src/                 пользовательский интерфейс
tests/                        unit- и API-тесты
docs/methodology.md           методология расчёта
data_report.md                аудит данных партнёра
```

## Установка и запуск

Требования: Python 3.11+, Node.js 20+ и npm. Исходные Excel-файлы партнёра
размещаются в `data/IEK/` и `data/Systeme electric/`. Если каталога данных нет,
backend запускается на демонстрационном наборе и сообщает `data_mode: demo`.

### Backend

```bash
python -m venv .venv
source .venv/bin/activate
python -m pip install -e '.[redis,dev]'
make api
```

Swagger будет доступен по адресу <http://localhost:8000/docs>, проверка состояния —
по <http://localhost:8000/health>.

Настройки необязательны: для локального запуска подходят значения по умолчанию.
При необходимости создайте `.env` в корне проекта, например:

```dotenv
DATA_DIR=data
CACHE_BACKEND=memory
NARRATOR_BACKEND=template
LOG_LEVEL=INFO
```

Для LLM-формулировок задайте `NARRATOR_BACKEND=openai`, `OPENAI_API_KEY`,
`OPENAI_BASE_URL` и `OPENAI_MODEL`. Секреты не добавляйте в Git.

### Frontend

В отдельном терминале:

```bash
cd frontend
npm ci
npm run dev
```

Интерфейс откроется по адресу <http://localhost:5173>. Vite проксирует запросы
`/api` на backend по адресу `http://localhost:8000`.

### Docker

Файл `.env` требуется Docker Compose, но может быть пустым:

```bash
touch .env
docker compose up --build -d
```

Этот compose-файл поднимает backend на порту `8000`; frontend запускается отдельно.
Необязательный Redis включается командой:

```bash
docker compose --profile redis up --build -d
```

## Как проверить решение

### Сценарий для жюри

1. Запустите backend и frontend по инструкции выше.
2. Откройте <http://localhost:5173> и на экране «Данные» нажмите запуск расчёта.
3. На экране рекомендаций проверьте группировку по поставщикам, статусы, срочность
   и журнал шагов агента.
4. Откройте позицию и изучите историю, прогноз и формулу по шагам.
5. Измените рекомендуемое количество, обязательно указав причину.
6. В разделе проверки заказа отправьте версию на согласование, переключите демо-роль
   на руководителя и утвердите её.
7. Скачайте XLSX. До утверждения экспорт возвращает конфликт, а поставщику файл
   никогда не отправляется.
8. Откройте экран «Проверки ТЗ»: все пять сценариев должны завершиться успешно.

Те же проверки без интерфейса:

```bash
curl http://localhost:8000/health
curl http://localhost:8000/api/v1/selfcheck
curl -X POST http://localhost:8000/api/v1/orders/calculate \
  -H 'Content-Type: application/json' \
  -d '{"lead_time_days":45,"method":"smoothed"}'
```

Автоматическая проверка проекта:

```bash
make test
make lint
cd frontend && npm run build && npm run lint
```

Тесты покрывают нормализацию обоих форматов Excel, влияние входных источников,
сезонность, тренд, stockout, выбросы, MOQ, группировку и объяснения, агентные
ветвления, ручные правки, роли, версии, утверждение, экспорт и запрет маршрута
отправки поставщику.

## Данные и интеграции

Проект использует 12 Excel-книг двух поставщиков:

- помесячные продажи — основной источник спроса;
- помесячные остатки — остатки и признаки stockout;
- динамика продаж — поиск разовых крупных накладных;
- товар в пути — уменьшение потребности до горизонта поставки;
- MOQ/кратность — округление заказа;
- сезонность — общая проверка сезонного профиля.

Ключ объединения — `Номенклатура.Код` / `Код 1с`. Результат экспортируется в XLSX
с отдельным листом на поставщика и сводным листом либо в CSV. Прямая интеграция
с базой 1С, почтой и системами поставщиков отсутствует.

### Загрузка выгрузок через интерфейс

При старте данные читаются из `data/`. Обновить их без перезапуска можно с экрана
«Данные»: выбрать поставщика, приложить его xlsx-выгрузки (те же шесть отчётов 1С),
нажать «Загрузить». `POST /api/v1/imports` принимает файлы и отвечает сразу, чтение
идёт в фоне; статус и отчёт о качестве данных — `GET /api/v1/imports/{id}`. При успехе
данные этого поставщика заменяются целиком, другого — остаются; версии расчёта и ручные
правки сбрасываются, потому что считались по старому снимку, а в шапке появляется
отметка «загружено через интерфейс». Неполный набор файлов даёт статус `failed`
с причиной, данные при этом не меняются. Исходные файлы не изменяются, загруженные
лежат во временном каталоге вне `data/`. Файлы распознаются по именам партнёра
и требуют его названий колонок; сопоставление колонок в интерфейсе — следующий шаг.

## Основные API

| Метод | Путь | Назначение |
|---|---|---|
| `POST` | `/api/v1/orders/calculate` | быстрый расчёт рекомендаций |
| `GET` | `/api/v1/orders/{code}` | расчёт и объяснение одного SKU |
| `POST` | `/api/v1/agent/runs` | расчёт с проверками агента и новой версией |
| `POST` | `/api/v1/drafts` | создать версию без агента |
| `PATCH` | `/api/v1/drafts/{v}/lines/{code}` | исправить количество с причиной |
| `POST` | `/api/v1/drafts/{v}/approve` | утвердить актуальную ревизию |
| `GET` | `/api/v1/drafts/{v}/export` | выгрузить утверждённую версию |
| `GET` | `/api/v1/selfcheck` | выполнить пять проверок ТЗ |
| `POST` | `/api/v1/imports` | загрузить выгрузки поставщика (multipart, фон) |
| `GET` | `/api/v1/imports/{id}` | статус импорта и отчёт о качестве данных |
| `GET` | `/health` | состояние компонентов и режим данных |
| `GET` | `/metrics` | число запросов и p50/p95 латентности |

Полный актуальный контракт доступен в Swagger после запуска.

## Ограничения текущей версии

- срок поставки отсутствует в исходных данных и задаётся параметром;
- у части партий Systeme Electric нет ETA; для IEK дата извлекается из заголовка;
- ID клиента отсутствует, поэтому вместо него используется номер накладной;
- транзакционные файлы покрывают не всю помесячную историю;
- импорт распознаёт файлы по именам партнёра и его названиям колонок; сопоставление
  колонок в интерфейсе, тренды по категориям и хронологический backtest пока не
  реализованы;
- роли являются демонстрационными: полноценной аутентификации нет;
- версии и журнал хранятся в памяти одного процесса и теряются после перезапуска;
- формат XLSX использует код 1С и согласованные поля, но загрузку в конкретную
  конфигурацию 1С нужно подтвердить у партнёра;
- публичная deployed-версия в репозитории не указана. Проект запускается локально
  или через Docker по инструкции выше.
