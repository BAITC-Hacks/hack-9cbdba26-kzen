# Кейс: автоматизация формирования заказов поставщикам

Партнёр: ТОО «Электрокомплект» (ekt.kz), дистрибьютор электротехники.
Трек «Логистика», HackAlem AI, 5 часов.

## Задача одной фразой

Менеджер отдела закупа считает потребность в пополнении склада вручную в Excel.
Из-за трудоёмкости расчёт делается редко, поэтому по одним позициям склад
затоварен, по другим дефицит. Нужен сервис, который считает рекомендованные
заказы поставщикам с обоснованием по каждой позиции.

**Пользователь:** менеджер отдела закупа.
**Сценарий:** запускает расчёт по складу или категории → получает список заказов
с обоснованием → проверяет, правит → утверждает.

**Запрещено** отправлять заказ поставщику без подтверждения человека.
Значит последний шаг интерфейса — всегда подтверждение, а не автоотправка.

## Данные

Два набора: `data/IEK/` и `data/Systeme electric/`, по шесть xlsx в каждом.
Имена файлов в архивах в cp437 — распаковывать через Python с перекодировкой,
иначе получите мусор и ошибки «File name too long».

| Файл | Что внутри | Как использовать |
|---|---|---|
| Ежемесячные продажи ... | артикул × месяц, штуки, янв.2024–сент.2026 | **основной источник спроса** |
| Ежемесячные остатки ... | артикул × месяц, «нач. остаток» | остатки и вывод stockout |
| Динамика продаж ... | транзакции: дата, номер накладной, код, склад, количество | **только** поиск разовых крупных заказов |
| Товар в пути / Путь ... | количества по открытым заказам поставщику | вычитается из потребности |
| MOQ / Кратность | минимальная партия к отгрузке | округление заказа |
| Сезонность | помесячные суммы **в деньгах по всей компании** | глобальный индекс, не по артикулам |

Объёмы (проверено): ИЭК — 171 604 строки транзакций, 58 049 накладных,
2151 артикул в транзакциях, 2854 артикула в остатках, MOQ на 1939 позиций,
товар в пути на 2642 позиции по 6 заказам. Systeme Electric — 77 314 строк
транзакций, ~500 артикулов.

Ключ связи между файлами — **`Номенклатура.Код` / `Код 1с`** (вид `300200428_`).
Не наименование: оно обрезано и неуникально.

## Файл, который важнее остальных

`Systeme electric/Товар в пути_SystemElectric на 22.09.2026.xlsx`, лист `TDSheet`,
60 колонок — это **действующая Excel-модель менеджера**, а не просто товар в пути.

Колонки: `Категория 2026`, `СС реал` (себестоимость), продажи по каждому месяцу
2024–2026, `Сумма последние 12 мес`, `Ср мес за последние 12 мес`, `Кэф. Роста`,
`Кэф. Сез-ти`, остатки по складам (`Витрина`, `Остаток ТЗ`, `РЦ ЕКТ`, `Рыскулова`,
`Розничный склад`), `Остаток`, `Зарезервировано`, `Свободный остаток`, `Запас`,
**`Заказ`** (пустая), `СЭ в пути`.

Отсюда два вывода:

1. Колонка `Заказ` — ровно то, что заполняет наш сервис. Формат вывода должен
   совпадать с этой таблицей, тогда он «совместим с текущей учётной системой»,
   как требует пункт 9 ТЗ.
2. Их формула видна: среднее за 12 месяцев × коэффициент роста × коэффициент
   сезонности, минус свободный остаток и товар в пути. **Это наш baseline.**
   Улучшения — четыре оси из Must have.

Показать «вот ваша текущая логика, вот где она теряет деньги» сильнее, чем
показать незнакомую модель.

## Ловушки в данных (проверено на файлах)

1. **Транзакции не покрывают всю историю.** По артикулу `200400085_` помесячный
   файл даёт 200 272 шт, сумма транзакций — 84 560. Файл транзакций охватывает
   2025–2026. Спрос считаем по помесячным файлам, транзакции — только для выбросов.
2. **Знак перевёрнут против ожидания.** В «Динамике продаж» продажи —
   **положительные** значения (171 471 строка), отрицательных всего 115, и это
   возвраты. Берём `> 0`, возвраты вычитаем отдельно.
3. **ID клиента в данных нет**, хотя ТЗ его упоминает. Есть только `Номер`
   накладной. «Крупная продажа одному клиенту» = одна накладная с аномальной долей.
   Проверено: у 4 артикулов одна накладная даёт больше половины всей истории,
   максимум в одной строке — 210 000 единиц.
4. **Stockout не дан, выводится из остатков.** Месяц считается провальным, если
   остаток 0 или пуст. Проверено: у 1106 артикулов из 2854 остаток нулевой больше
   трети месяцев, медиана по ассортименту — 15% месяцев без остатка.
5. **Сезонность в файле — деньги по всей компании**, не по артикулам. Индекс по
   товару считаем сами из помесячных штук; файл — глобальная проверка.
6. **MOQ:** у Systeme в `Кратность` стоят нули — трактовать как 1, иначе деление
   сломается. У ИЭК поле называется `Мин. разр. к отгр.`.
7. **Срок поставки в данных отсутствует.** В названиях заказов есть даты
   («РФ УТ-7583 от 31 августа 2026»), можно оценить, но лучше сделать параметром
   с умолчанием и спросить у партнёра.
8. **Шапки многоуровневые:** в помесячных файлах вторая и третья строки —
   «Количество» и «нач. остаток». Читать со `skiprows`, иначе всё станет строками.

## Расчётное ядро

Порядок по каждому артикулу:

```
история продаж (помесячно)
  → убрать разовые крупные накладные       (Must have 4)
  → компенсировать месяцы stockout          (Must have 3)
  → базовый спрос = среднее за 12 мес
  → × коэффициент роста                     (Must have 2)
  → × коэффициент сезонности месяца поставки(Must have 2)
  → потребность на срок поставки + страховой запас
  → минус свободный остаток минус товар в пути (Must have 1)
  → округлить вверх до MOQ
  → срочность = запас в месяцах до прихода
```

Обучать нечего: это статистика и правила, а не ML. Пять часов уходят на логику
и объяснимость, а не на подбор гиперпараметров. LLM нужен максимум для
формулировки обоснования словами — расчёт всегда делает код.

## Обоснование строки (Must have 5)

Собирается из компонентов формулы, например:

> Средние продажи 42 шт/мес, сезонность октября +18%, тренд +12%,
> компенсация за 2 месяца отсутствия +15 шт, исключена разовая накладная на 100 шт,
> срок поставки 45 дней, свободный остаток 30, в пути 0 → заказать 120 шт (кратность 10).

Каждое число в тексте должно приходить из расчёта. Сгенерированных цифр быть не может.

## Must have как тесты

Пункт 7 ТЗ написан в виде проверок — делаем их автотестами и показываем жюри:

1. изменение товара в пути меняет результат;
2. у сезонного товара прогноз повторяет сезонный профиль, а не среднее;
3. при зафиксированном stockout потребность выше, чем по «сырым» продажам;
4. искусственно добавленный разовый крупный заказ не раздувает рекомендацию;
5. каждая строка имеет обоснование, список группируется по поставщикам.

Экран «Самопроверка», где эти пять проверок прогоняются вживую с показом
«до/после» — самый дешёвый способ показать соответствие критериям.

## Цифры для защиты

- товара нет на складе в среднем 15% месяцев, у 39% ассортимента — больше трети года;
- одна накладная может составлять 100% истории продаж артикула — вот что ломает
  текущий расчёт;
- бэктест: посчитать заказы на начало 2026 нашей формулой и сравнить с фактом
  по остаткам — сколько stockout можно было избежать и сколько лишнего запаса не купить.
