# Контекст проекта

**Кейс описан в `CASE.md` — прочитай его перед любой работой с данными.**
Там структура файлов партнёра, проверенные ловушки в данных и формула расчёта.
Для Codex тот же контекст продублирован в `AGENTS.md`.

Хакатон на 5 часов. Каркас ML-сервиса уже написан, протестирован и работает.
Задача — быстро адаптировать его под кейс, **не переписывая архитектуру**.

Отвечай по-русски. Комментарии в коде тоже на русском, объясняй в них «почему»,
а не «что»: что делает строка, видно из кода.

## Что уже есть и работает

- FastAPI на чистой архитектуре: `domain` → `application` → `api`, адаптеры в `infrastructure`
- Три реализации модели: `dummy` (заглушка), `artifact` (обученный пайплайн), `llm` (NVIDIA без обучения)
- Кэш `memory`/`redis`, хранилище `memory`/`parquet`/`postgres`
- Обучение: `ml/src/train.py` с валидацией, holdout, подбором порога
- Текстовые объяснения: шаблон или NVIDIA NIM
- 36 тестов, линтер чист, Docker с профилями
- Замеры: одиночный запрос p50 ~8 мс, батч 0.11 мс на объект

Ничего из этого не нужно создавать заново. Прежде чем писать новый файл,
проверь, нет ли уже подходящего.

## Жёсткие правила

Нарушение любого из них — это регресс, даже если код работает.

1. **`domain/` не импортирует фреймворки.** Ни FastAPI, ни Pydantic, ни CatBoost,
   ни SQLAlchemy, ни pandas. Только стандартная библиотека.
2. **Роутер не содержит логики кейса.** Появился `if` про бизнес-правило — переноси в use case.
3. **Эндпоинты с инференсом объявляются через `def`, не `async def`.** CPU-задача
   в корутине блокирует event loop и весь сервис.
4. **Препроцессинг живёт внутри sklearn Pipeline**, а не в API. Иначе обучение
   и инференс разойдутся, и модель начнёт молча врать — по метрике этого не видно.
5. **Порядок признаков берётся из `metadata.json`.** Перепутанные колонки не дают
   ошибки, модель просто выдаёт чушь.
6. **Новая абстракция — только при второй реализации.** Интерфейс ради интерфейса
   это минус к архитектуре, а не плюс.
7. **Никаких новых тяжёлых зависимостей** без явной просьбы. Пять часов.
8. **Секреты только в `.env`**, который в `.gitignore`. Ключ в коде — это чужие
   расходы по счёту команды.

## Команды

```bash
make data     # синтетический датасет
make train    # обучение + артефакт
make api      # сервис на :8000/docs
make test     # 36 тестов, без внешних сервисов
make lint     # ruff
python scripts/bench.py   # замер латентности
```

Тесты и линтер гоняй после каждого заметного изменения, не в конце.

## Куда вносить правки под кейс

| Что меняется | Файл |
|---|---|
| данные | `data/dataset.parquet` или `DATASET_PATH` |
| таргет, тип задачи, валидация | `ml/src/config.py` |
| признаки кейса | `ml/src/features.py`, функция `add_case_features` |
| названия сущностей | `backend/app/domain/entities.py` (`Subject` → сущность кейса) |
| бизнес-правила и пороги | `backend/app/application/use_cases/predict.py` |
| состав сервиса | `.env` или `backend/app/core/presets.py` |

Архитектурные файлы (`ports.py`, `container.py`, `deps.py`, `errors.py`,
`middleware.py`) трогать обычно не нужно.

## Выбор подхода

**Для текущего кейса обучение не нужно вообще**: это расчётное ядро (статистика,
сезонность, тренд, выбросы, MOQ), а не ML. LLM нужен максимум для формулировки
обоснования словами — все числа считает код. Подробности в `CASE.md`.

Общее правило на случай смены задачи:

- **данные табличные и размеченные** → `make train`, это 10 минут и лучшее качество;
  `MODEL_BACKEND=artifact`
- **текст, нет разметки, нужна генерация** → `MODEL_BACKEND=llm` плюс
  `LLM_TASK_DESCRIPTION`; обучения нет вообще
- **текст есть, но задача табличная** → эмбеддинги как признаки:
  `python -m ml.src.text_features --column <колонка>`, дальше обычное обучение

Во всех случаях интерфейс `ModelPort` один и тот же, остальной сервис не меняется.

## Что нужно жюри

Собирай по ходу работы в `pitch_notes.md`:

- находки в данных с цифрами;
- метрику: `baseline → финал`, или, если обучения нет, долю совпадений
  на 50–100 размеченных примерах (без измеримой цифры защита слабая);
- топ факторов влияния на языке бизнеса;
- латентность из `scripts/bench.py`;
- оценку эффекта: охват × точность × конверсия действия × маржа.

## Частые ошибки в этом проекте

- забыть `MODEL_BACKEND=artifact` после обучения и показывать заглушку;
- считать признаки в API отдельно от `features.py` — гарантированный рассинхрон;
- ставить LLM на путь `/predict` вместо отдельной ручки: 8 мс превращаются в секунды;
- случайный holdout на временных данных — метрика завышается;
- радоваться ROC-AUC выше 0.97 вместо поиска утечки.

Коротко и по делу. Не переписывай рабочий код ради красоты. Если предлагаешь
решение с компромиссом — назови цену вслух: что теряем по скорости, качеству
или времени. Если видишь, что запрос уводит от заморозки или ломает правила
выше — скажи об этом прямо, а не выполняй молча.
