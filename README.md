# Расчёт заказов поставщикам

Сервис считает рекомендованные заказы для пополнения склада ТОО «Электрокомплект»:
история продаж и остатков → потребность по каждому артикулу → список заказов
по поставщикам с обоснованием каждой строки → проверка и утверждение менеджером.

Кейс, карта данных и ловушки в файлах партнёра — в `CASE.md`.

## Что внутри

**Расчётное ядро, а не ML.** Статистика, сезонность, тренд, выбросы, кратность.
Обучения нет: всё считается за миллисекунды по 36 числам на артикул.

**Два метода прогноза, переключаются в запросе:**

| Метод | Что делает | Зачем |
|---|---|---|
| `baseline` | среднее за 12 мес × рост × сезонность | повторяет текущую формулу партнёра, точка отсчёта |
| `smoothed` | экспоненциальное сглаживание, отдельная ветка для редких продаж | реагирует на изменения спроса быстрее |

**Пять требований ТЗ как живые проверки.** `GET /api/v1/selfcheck` прогоняет
их на синтетических артикулах и показывает «до/после» по каждому.

## Для Claude Code

В корне лежит `CLAUDE.md` — контекст проекта: правила слоёв, команды, куда вносить
правки под кейс, тайминг и заморозка. В `.claude/skills/` пять скиллов, которые
подхватываются автоматически: разбор кейса, обучение, архитектура бэкенда,
скорость инференса, подготовка защиты. Отдельно настраивать ничего не нужно —
достаточно открыть папку проекта.

## Архитектура

```
        HTTP
         │
    ┌────▼─────────────────────────────────────────┐
    │  api/         роутеры, схемы, ошибки          │
    ├──────────────────────────────────────────────┤
    │  application/ сценарии кейса (use cases)      │
    ├──────────────────────────────────────────────┤
    │  domain/      сущности, порты, правила        │  ← ничего не импортирует
    ├──────────────────────────────────────────────┤
    │  infrastructure/  CatBoost · DuckDB · Redis   │  → реализует порты
    └──────────────────────────────────────────────┘
         ▲
    core/container.py — единственное место, где выбираются реализации
```

Зависимости направлены внутрь: `api → application → domain`, а `infrastructure`
реализует интерфейсы домена. Практический смысл — не красота схемы, а то, что
модель, кэш и хранилище меняются строкой в `.env`, а тесты идут без Redis и Postgres.

### Как задать состав сервиса

Два равноправных способа: настройками или прямо в коде.

**Способ 1 — настройки (`.env`).** Удобно переключать на ходу, ничего не пересобирая.

| Настройка | Значения | Когда менять |
|---|---|---|
| `MODEL_BACKEND` | `dummy`, `artifact`, `llm` | `artifact` после `make train`; `llm` если обучать некогда |
| `CACHE_BACKEND` | `memory`, `redis` | `redis` только при нескольких воркерах |
| `STORAGE_BACKEND` | `memory`, `parquet`, `postgres` | `parquet` для датасета кейса |

**Способ 2 — сборка в коде.** Когда состав решён один раз и навсегда, явная сборка
честнее: её видно при чтении, она проверяется линтером и не ломается от опечатки в `.env`.
Готовые сборки лежат в `app/core/presets.py` — `dev` (заглушки), `demo` (артефакт +
parquet + кэш в памяти), `scaled` (то же с Redis), `no_training` (оценка через LLM). Переключение — одна строка в `main.py`:

```python
from app.core.presets import demo
app = create_app(container_factory=demo)
```

Своя сборка пишется там же и может комбинироваться с настройками — передавайте
только то, что хотите зафиксировать:

```python
async def my_setup(settings):
    return await build_container(
        settings,
        model=ArtifactModel(Path("ml/artifacts/model.joblib"),
                            Path("ml/artifacts/metadata.json")),
        storage=ParquetStorage(Path("data/dataset.parquet"), "subject_id"),
        # кэш не передан — возьмётся из настроек
    )
```

**Разница в поведении при сбое.** По настройкам сервис деградирует, но живёт: нет модели —
работает заглушка, нет Redis — кэш в памяти, нет датасета — пустое хранилище, а `/health`
отдаёт `degraded` с причинами. Упавшее на защите демо стоит дороже, чем демо без кэша.
Переданный же явно компонент не подменяется: если в коде написано «здесь артефакт»,
сервис упадёт при старте, а не сделает вид, что всё хорошо.

## Эндпоинты

| Метод | Путь | Зачем |
|---|---|---|
| POST | `/api/v1/orders/calculate` | заказы по поставщикам с обоснованием |
| GET | `/api/v1/orders/{code}` | карточка артикула: сколько заказать и почему |
| GET | `/api/v1/selfcheck` | пять проверок из пункта 7 ТЗ вживую |
| GET | `/api/v1/stats` | номенклатура, поставщики, доля месяцев без товара |
| GET | `/health` | `ok` или `degraded` с причинами |
| GET | `/metrics` | счётчики и p50/p95 латентности |

Параметры расчёта (`lead_time_days`, `coverage_months`, `safety_factor`, `method`)
передаются в запросе — менеджер может крутить их в интерфейсе и видеть,
как меняется заказ.

## Логика расчёта

```
история продаж по месяцам
  → срезать разовые крупные продажи        (Must have 4)
  → компенсировать месяцы без товара        (Must have 3)
  → прогноз: рост и сезонность              (Must have 2)
  → потребность на срок поставки + запас
  → надбавка страхового запаса по категории (Must have 1)
  → минус свободный остаток и товар в пути  (Must have 1)
  → округлить до кратности отгрузки
  → срочность и обоснование                 (Must have 5)
```

Для Systeme Electric категория влияет на страховой запас, а не только фильтрует
список: категория `1` добавляет 10 процентных пунктов к заданному менеджером
`safety_factor`, категория `2` — 5 п.п., категория `3` — без надбавки. Итоговый
страховой коэффициент ограничен 100%. Категория и применённая надбавка входят в
структурированное обоснование строки. Для неизвестной категории используется
только заданный менеджером страховой запас — сервис не придумывает приоритет.

### Как исключаются разовые крупные продажи

Очистка выполняется детерминированно до компенсации stockout и до прогноза:

1. Транзакции используются как подтверждение клиентского сценария, но не заменяют
   помесячную историю. Накладная считается кандидатом, если её количество не менее
   чем в 10 раз выше медианной накладной по SKU и составляет не менее 50% объёма
   доступной транзакционной истории. Из соответствующего месяца вычитается только
   превышение над типичной накладной; номер накладной сохраняется как evidence.
2. Затем проверяются помесячные значения. Нужно минимум четыре положительных месяца.
   Ожидаемый уровень — медиана того же календарного месяца в другие годы; если таких
   наблюдений нет, используется медиана всей положительной истории. Сезонный эталон
   ограничен тремя глобальными медианами, чтобы прошлый выброс не завысил порог.
3. Месяц признаётся выбросом при продажах выше трёх ожидаемых уровней. Он не удаляется:
   значение заменяется ожидаемым уровнем, сохраняя обычный спрос этого месяца.
4. Только после этого месяцы подтверждённого отсутствия товара компенсируются средним
   спросом месяцев с наличием. Такой порядок не позволяет выбросу раздуть компенсацию.

Сравнение с тем же календарным месяцем защищает повторяющийся сезонный пик: высокий
ноябрь два года подряд остаётся сезонностью, а не ошибочно удаляется как разовый заказ.
Ограничение метода: ID клиента в выгрузках нет, поэтому номер накладной используется
как проверяемый proxy клиента; транзакции покрывают не всю помесячную историю.
Реализация находится в `domain/demand.py`, пороги поиска накладных — в
`infrastructure/storage/excel_normalizer.py`.

## Тесты

```bash
make test
```

24 теста. Покрыто: очистка истории (выбросы, stockout, сезонность, тренд),
группировка по поставщикам, кратность отгрузки, влияние срока поставки,
переключение методов, ошибки 404 и 422, и все пять требований пункта 7 ТЗ.
Ни один тест не требует внешних сервисов и файлов партнёра.

## Скорость

| Операция | Время |
|---|---|
| расчёт по одному артикулу | 0.8 мс |
| самопроверка (5 требований ТЗ) | 2 мс |

Расчёт по всей номенклатуре (~3000 артикулов) укладывается в доли секунды,
поэтому никакой базы данных и фоновых задач не нужно.

## Решения и отказы

| Решение | Почему | От чего отказались |
|---|---|---|
| Расчёт вместо ML | задача решается статистикой; обучение не дало бы выигрыша за 5 часов | обученная модель, CatBoost, артефакты |
| Порты и адаптеры | реализации меняются строкой в `.env` или сборкой в коде, тесты без внешних сервисов | абстракции ради абстракций: интерфейс только там, где есть вторая реализация |
| Очистка истории в домене | нужна любому методу прогноза, а не конкретному | дублирование чистки в каждом прогнозисте |
| Номенклатура в памяти | 3000 артикулов × 36 месяцев считаются за доли секунды | база данных ради 15 МБ Excel |
| Кэш в памяти по умолчанию | при одном воркере быстрее Redis: нет сети и сериализации | Redis в обязательных зависимостях |
| `def` вместо `async def` на расчёте | CPU-задача в корутине заблокировала бы весь сервис | асинхронность ради асинхронности |
| Профили в compose | лишний сервис — лишняя точка отказа на демо | поднимать всё сразу |
| Деградация вместо падения | демо должно работать даже при отказе инфраструктуры | жёсткие проверки на старте |
| LLM отдельной ручкой | объяснение стоит сотни мс, оценка — единицы; связывать их значит потерять скорость | LLM внутри `/predict` |

Эта таблица — готовый слайд. Умение объяснить, от чего отказались и почему,
ценится жюри выше, чем длинный список подключённых технологий.
